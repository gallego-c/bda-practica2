\section{Introduction}
The goal of this project is to continue building a complete end-to-end data science pipeline by extending the previous work with a knowledge graph layer and graph-based analysis. The new scope focuses on how the RDF representation is designed, how it is queried, and how graph embeddings can support downstream modeling.

\section{Previous work}

In the previous project, we created a 5-stage pipeline integrating 3 different datasets. They were from the healthcare domain, focusing on cardiovascular diseases: the \textit{Cardiovascular Disease} dataset, the \textit{Heart Disease Health Indicators} dataset from BRFSS, and the \textit{Cleveland Heart Disease} dataset. Our goal was to evaluate the risk of developing such diseases based on both medical and behavioral factors.\\

The architecture as mentioned was divided in 5 stages. The first Zone was the Landing Zone. It ingests three configured Kaggle datasets and stores each extraction as a timestamped raw Parquet snapshot. Keeping ingestion separate from downstream transformations and serves as a stable reference point.\\

The second was the Formatting Zone, that standardizes the data to make sure that the three source datasets are consistent and structured in the same way. Spark is used and the datasets are aligned at the schema level. Then, we use DuckDB to store the formatted data for easy access and a lightweight storage solution.\\

The Trusted Zone is the third layer of the data pipeline, where transformations are applied, strict data-quality constraints and rules are enforced on the standardized data. This zone ensures that the data meets necessary quality standards before moving to the next stages.\\

In the Exploitation Zone, trusted data is integrated and processed to create the combined dataset used in analysis. Any discrepancies between datasets are resolved, and the data is transformed into the unified structure. The data is then aggregated into a singular dataset, the canonical table, thanks to a vertical union.\\

Finally, the Analysis Zone trains two reproducible \emph{integrated} machine learning pipelines over the canonical table. Both analytical pipelines follow the same execution template with some difference in the models. 

\section{Project Overview}
This project keeps the original five-zone data engineering structure but adds a semantic layer on top of the integrated health data. The main contribution is not only a new storage format, but a graph model that represents records, indicators, population groups, and outcomes in a way that is suitable for academic analysis and reusable querying.

The report therefore emphasizes two graph-oriented tasks: SPARQL exploration of the generated RDF and KGE-based analysis over graph-derived representations. Both are meant to demonstrate how the same integrated dataset can support relational and semantic analytics.

\section{Project improvements}
The key improvement is the inclusion of a knowledge graph layer built from the trusted and exploited health data. Instead of treating the final table as the only analytical artifact, the project now also exposes the data through RDF, which makes the relationships between records, shared indicators, and population groups explicit.

Another improvement is the formalization of the RDF schema. We created classes such as HealthRecord, Dataset, PopulationGroup, AgeGroup, Gender, Indicator, Outcome, and AggregateMeasurement, and connected them with object and data properties so the graph can be queried in a structured and academically reusable way. Beyond a flat RDF schema, these classes are organized into a real RDFS taxonomy using \texttt{rdfs:subClassOf} (under abstract super-classes Concept, DemographicConcept, HealthConcept, and Observation) and \texttt{rdfs:subPropertyOf} (grouping the individual factor relations under a shared super-property). This enables type-level and property-level entailment through RDFS reasoning.

Finally, the analytical focus shifts toward graph-based experimentation. The SPARQL layer supports semantic querying of the graph, while the KGE stage transforms that same graph into vector representations that can be used in predictive tasks, giving the report a stronger emphasis on knowledge extraction rather than only tabular inference. We additionally train a hybrid model that combines tabular clinical features with KG embeddings, and a comparison stage that quantifies the added value of the graph-derived features against purely tabular baselines.

\section{Knowledge graphs}
The knowledge graph was built to represent the integrated cardiovascular data in a semantic model that is more expressive than a flat table. Each trusted record becomes a HealthRecord instance, the source datasets are modeled as Dataset nodes, and the shared conceptual layers are represented through PopulationGroup, AgeGroup, Gender, Indicator, and Outcome classes.

The RDF schema was designed for academic clarity and reusability. Object properties such as fromDataset, belongsToAgeGroup, hasGender, belongsToPopulationGroup, hasObservedRiskFactor, and hasOutcome connect records to their context, while data properties store metadata such as run identifiers, indicator labels, aggregate values, and observation counts. This makes the graph suitable for provenance-aware analysis and for demonstrating how heterogeneous datasets can be aligned under a common vocabulary.

To make the schema a genuine RDFS taxonomy rather than a flat list of classes, the concrete classes are arranged under abstract super-classes through \texttt{rdfs:subClassOf}: demographic classes (AgeGroup, Gender, PopulationGroup) and health classes (Indicator, Outcome) descend from a common Concept hierarchy, while HealthRecord and AggregateMeasurement are both kinds of Observation. Similarly, the specific factor predicates (hasObservedRiskFactor, hasProtectiveFactor, hasObservedFactor) are grouped under a shared super-property via \texttt{rdfs:subPropertyOf}. We then materialize the RDFS entailment (closure under the \texttt{rdfs7} and \texttt{rdfs9} rules) so that, for example, every AgeGroup instance is also inferred to be a Concept, and any specific factor assertion is also retrievable through the general super-property. One of the SPARQL queries explicitly relies on this sub-property inference to demonstrate the value of reasoning.

\section{Querying with SPARQL}
SPARQL was used to interrogate the graph at the semantic level rather than through SQL-style joins. The query set explores how records are distributed across population groups, which indicators are shared across datasets, how outcome rates vary by age group, and which risk factors co-occur in positive cases.

These queries are important because they show the analytical value of the graph itself. Instead of only extracting rows, the project can ask questions about concepts and relationships, which is more appropriate for academic exploration of health data integration.

Table~\ref{tab:sparql-queries} lists representative questions and the type of graph result each one targets.

\section{KGE-based analysis}
The KGE-based analysis uses the knowledge graph as a source of structured features. Graph entities and relations are transformed into embeddings using standard Knowledge Graph Embedding methods, and those embeddings are then used as inputs for predictive models. In this way, the graph is not only a descriptive layer, but also a representation learning layer.

This stage complements the SPARQL exploration because it turns semantic structure into numerical vectors that can support downstream prediction. The embeddings are learned with the PyKEEN library, training canonical translational and bilinear models (TransE, DistMult, and ComplEx) over the RDF triples and selecting the best model by Mean Reciprocal Rank (MRR); a TruncatedSVD factorization of the typed adjacency is kept as a fallback. The important point is that the graph captures context that is not available in the tabular form alone, so the embedding-based analysis can exploit relationships between datasets, population groups, and indicators while remaining compatible with standard machine learning workflows.

Table~\ref{tab:kge-pipeline} shows the main steps followed by the KGE pipeline and the type of representation each step produces.

Second, it serves as a representation-learning substrate for KGE, where the structural information of the RDF graph is transformed into features that a model can use.

\section{Hybrid modeling and comparison}
To assess whether the knowledge graph contributes signal beyond traditional tabular machine learning, we train a hybrid model that concatenates the best tabular clinical features with the KG node embeddings, and we compare four pipelines on the same outcome: a tabular core baseline, a tabular enriched baseline, a KG-embedding-only model, and the hybrid model. A dedicated comparison stage collects the test-set metrics (accuracy, precision, recall, F1, ROC-AUC, and PR-AUC) of every pipeline into a single report.

The results confirm two findings. First, the KG-embedding-only model reaches performance comparable to the tabular baselines while relying exclusively on graph-derived features, which validates that the graph encodes meaningful disease structure. Second, the hybrid model combines both feature spaces, and the difference with respect to the tabular baseline quantifies the complementary value of the relational context captured by the graph. This empirical comparison is the final piece of evidence that the knowledge graph is not only a descriptive artifact but also a useful source of predictive features.
